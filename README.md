## v4 聊天体验变化

### 主动聊天改成两层
1. **对话惯性**：一轮回复结束后，如果用户没有继续说话，45~135 秒后会进行一次本地后台检查。模型判断话题是否还有自然余韵；有必要时联系人会自己再补一句。用户在等待期间一旦发新消息，本次跟进自动取消。
2. **隔段时间主动联系**：熟悉联系人不再要求 8 小时静默 + 18 小时主动间隔。根据熟悉程度，约静默 2.5~6 小时后进入候选；非事件型主动联系约每 3 小时得到一次判断机会，真正发不发仍由人物模型决定。

Android WorkManager 受系统省电影响，后台时间不是秒级精确。

### 对话连贯性
- 修复“当前用户消息既在最近聊天里出现、又作为最新消息重复出现”的问题。
- 系统提示明确允许“不追问”“只反应一句”“自然停住”，减少每轮都像问答助手。
- 多条消息的间隔改由 App 根据文字长度计算，不再完全依赖模型随手生成 delay_ms。

### 顶部按钮
- 返回按钮扩大到 56dp 触控区。
- 右上角 `···`、`+` 等扩大到约 64×58dp。
- `保存/完成` 最小宽度 72dp、高度 56dp，字号增大。


## v5 新增

### 休眠模式
路径：
`我 → 设置 → 休眠模式`

开启后：
- 手动聊天正常回复
- 刚聊完后的主动补一句关闭
- 几小时后的主动聊天关闭
- 事件主动消息关闭

关闭后恢复主动聊天调度。

### 快速闲聊
短消息且没有“分析/解释/方案/代码”等复杂意图时进入快速路径：
- 最近上下文从最多 12 条缩到最多 6 条
- 长期记忆从最多 7 条缩到最多 3 条
- 最大生成长度限制为 220 tokens
- 可以在 `我 → 设置 → AI 服务 → 快速聊天模型` 单独填写一个更快的 RunAPI 模型 ID
- 留空则继续使用联系人的模型

复杂问题仍走完整上下文，避免为了快牺牲质量。

### 清理后台后的主动消息
Realtek 的主动消息通过 Android WorkManager 注册给系统调度。
普通把 App 从最近任务划掉后，系统仍有机会重新启动相关后台组件并发出通知。
但如果在 Android 系统设置里执行“强行停止”，系统会阻止应用继续后台运行，直到用户再次手动打开。

纯本地方案受 Android Doze、厂商省电策略影响，无法达到微信/FCM 服务端推送那种绝对实时性。


## v6 对话内核

v6 专门解决此前剩下的四个聊天问题。

### 1. Conversation Planner
每一轮不再直接把用户消息扔给人物模型。

先经过 ConversationPlanner，得到：
- mode：闲聊 / 情绪反应 / 回答 / 修复理解 / 连续讲话 / 倾听等
- floor：是否立即让出话轮、轻度占住话轮、持续占住话轮
- maxStages：这一轮最多说几段
- responseStyle：这一轮的具体交流方式
- askFollowup：是否适合追问
- selectedMemoryIds：这轮真正相关的长期记忆

明确的简单闲聊使用本地 Planner，几乎没有额外网络延迟；
涉及“上次、之前、那个、后来、终于、明天、结果”等语义指代，
或需要复杂规划时，再调用对话规划模型做语义重排。

### 2. 流式输出
普通文字聊天优先使用 OpenAI-compatible SSE：
`stream=true`

第一批 token 到达后，聊天气泡立即开始显示，不再必须等完整答案返回。

如果 RunAPI 某个通道不支持流式：
- 自动识别非 SSE 返回；
- 或遇到常见 stream 参数错误；
- 自动退回普通 Chat Completions；
- 不会因此让聊天完全失效。

### 3. 真正多阶段聊天
不再是“一次生成 3 条，再假装分开发”。

现在每个 stage 都是独立生成：
1. 第一段真正生成并流式显示；
2. 稍停；
3. 检查用户有没有插话；
4. Conversation Planner 重新判断是否还应该继续占住话轮；
5. 只有需要时才生成下一段。

用户中途一发消息，旧话轮后续阶段立即终止。

### 4. 连续讲话 / hold floor
用户说：
- “你继续说”
- “你说一会儿”
- “讲个故事”
- “我想听你说”
- “陪我聊会儿”
- “你多说点”

会进入 `talk_burst`。

这时联系人可以连续说 3~5 段，每段都是单独生成的聊天消息，
中间自然停一下，而且每次继续前都会检查用户是否插话。

这模拟真人“拿住话轮讲一会儿”，而不是一次性提前写完全部内容。

### 5. 语义记忆
v6 不再只靠关键词命中最终记忆。

流程变成：
- 本地先从长期记忆中组成候选池：
  - 高重要度
  - 最近记忆
  - 临近事件
  - open_loop 未完成话题
  - 有表面文字线索的记忆
- 最多约 40 条候选进入语义 Planner
- Planner 根据“意义”选择最多 8 条真正相关记忆

例如：
“明天终于轮到我了”
可以语义关联：
“用户周五进行论文答辩”

即使“轮到我”和“论文答辩”没有直接关键词重合。

### 6. 未完成话题
记忆整理增加：
`type = open_loop`

用于：
- “晚点告诉你结果”
- “明天出成绩”
- “这个事等会再说”
- 等待后续结果的问题

Planner 会优先把 open_loop 放入语义候选池。

### 7. 更接近人类轮流交流
v6 增加了这些规则：
- 不强制每轮追问
- 短消息优先短回应
- 用户展开时再展开
- 理解错时进入 repair，而不是辩解
- AI 可以 yield 让出话轮
- 也可以 hold floor 连续说一会
- 用户随时可以插话，中断 AI 后续阶段

## v7：Social Engine

v7 的重点不是增加普通功能，而是让联系人具有更连续的“社交行为”。

### 1. Persistent Social State
每个联系人本地保存：
- mood：当前聊天气氛
- conversation_energy：聊天活跃度
- social_drive：主动交流倾向
- current_topic：当前话题
- phase：对话阶段
- familiarity：熟悉度
- trust：交流信任度
- humor_comfort：玩笑接受度

这些值只用于控制聊天行为，不代表真实人的身体或现实生活状态。

### 2. Conversation State
Conversation Planner 现在额外维护：
- topic_label
- phase

所以系统能区分：
- 正在听用户讲故事
- 正在回应情绪
- 正在回答问题
- 正在修复误解
- 正在连续讲话
- 正在自然收尾

避免每一句都重新像“第一句话”一样处理。

### 3. AI Self History
新增 `ai_topic_history`：
记录联系人最近自己聊过的主题。

例如最近已经出现：
- self_fatigue
- self_sleep
- boredom

这些主题进入冷却，避免 AI 反复自己说：
“好累”
“好困”
“无聊”

### 4. Self-Repetition Guard
每条 AI 消息发送前会检查：
- 是否和最近 72 小时内的 AI 消息高度相似
- 是否属于正在冷却的自我状态主题
- 是否是上一轮已经说过内容的近似改写

如果重复：
1. 不直接发送；
2. 重新生成一次；
3. 第二次仍重复时，宁可不发，也不重复刷同一句。

“嗯 / 啊 / 哈哈”这类真人聊天常见的短 backchannel 不会因为文本相同被强行拦截。

### 5. Streaming Repetition Protection
流式回复不会一拿到第一个字符就立刻显示。
前几个字符先做一个很短的本地缓冲：
- “好累”
- “好困”
这类短重复可以在用户看到前被拦截。

正常且不重复的回复仍继续流式显示。

### 6. Topic Novelty
普通聊天允许一个话题连续聊几轮；
但主动聊天会优先避开最近已经主动聊过的自我状态和开场方式。

没有新东西可说时：
`send=false`

而不是为了完成“主动聊天任务”硬发一句。

### 7. Socially-Aware Proactive Timing
主动聊天不再只看固定小时数。

现在会同时考虑：
- familiarity
- social_drive
- open_loop 未完成话题
- 临近事件
- 最近一次主动消息

熟悉且互动意愿较高的联系人可以更自然地早点联系；
陌生或当前社交驱动力低时会更克制。

### 8. Memory Separation
长期记忆整理器明确区分：
- 用户事实
- 共同经历
- 未完成话题
- AI 联系人临时自述

AI 自己说“我累了/我困了/我无聊”不会再被错误写成长期记忆，
避免形成“摘要里有累 → 下次又说累 → 再写进摘要”的自我强化循环。

### 9. Identity Transparency
聊天方式会尽量自然，但联系人资料仍明确是 AI。
用户直接问身份时必须如实回答。
自然感来自交流连续性，不靠冒充真实人类或编造线下经历。


## v7.1 compile fix

修复 `RunApiGateway.streamChat()` 中 SSE 分支的 Kotlin 标签返回问题。

此前在 `call.execute().use { ... }` 内使用 `return@withContext`，
会令 `use` lambda 被推断成 `Unit`，而 `streamChat()` 需要 `String`，
从而产生：

- Argument type mismatch: Unit / String
- Return type mismatch: expected Unit, actual String

v7.1 已将这些返回改为 `return@use`，使 `use` 表达式正确返回 String。


## v7.2 compile fix

重写 `RunApiGateway.streamChat()` 的控制流。

v7.1 仍在 `use {}` lambda 内使用带标签的提前返回，
Kotlin 对 `use` / `try` 表达式进行类型推断时仍会把部分分支推断为
`Unit` / `Any`，导致 `String` 返回类型冲突。

v7.2 不再使用任何 `return@use` / `return@withContext` 来处理 SSE 分支，
而是把整个 `use {}` 写成一个纯 `if / else if / else` 的 String 表达式。
所有正常分支都直接产生 `String`，异常分支为 `Nothing`。

## v7.4：几秒级自主续聊

正在聊天时，不再使用旧的 45~135 秒 WorkManager “补一句”。

现在流程：

1. 联系人正常回复第一条；
2. 同时后台开始一次“是否继续聊”的判断；
3. 自然停顿约 1.5~4.5 秒；
4. 如果用户已经发新消息，立即终止；
5. 如果判断适合继续，联系人自己的模型再生成 1~3 条独立消息；
6. 每条之间再停约 1.5~4.5 秒；
7. 整个短续聊只做一次继续/停止决策，不会每发一条都重新调用 DeepSeek。

判断模型：
- 配置 DeepSeek 时：DeepSeek 负责“要不要继续、继续几条、沿什么方向”
- 没配 DeepSeek 时：自动退回海鲸

真正聊天内容：
- 海鲸联系人 → 仍由该联系人选择的海鲸模型生成
- DeepSeek 联系人 → 由该联系人选择的 DeepSeek 模型生成

因此 DeepSeek 不会替海鲸联系人直接写台词。

旧的 45~135 秒 ConversationFollowUpWorker 已禁用。
几小时级主动聊天仍保留，和正在聊天时的几秒级续聊是两套独立机制。


## v7.5 真人节奏优化

这一版没有加入“用户正在输入检测”。

### 普通聊天
- 大多数情况只发 1 条。
- 有聊头时，才有机会在约 1.1~3.8 秒后自然补 1 条。
- 普通场景最多只补 1 条，不再轻易连续 3 条。
- 是否进入“续聊判断”先经过本地节奏门控，不是每句话都调用 DeepSeek。

### 明确让 AI 多说
当用户明确说：
- 继续说
- 多说点
- 接着讲
- 我听着
- 陪我聊会儿

才允许多条连续发言。

### 不同联系人节奏不同
联系人自己的核心性格和说话方式会影响：
- 是否容易补一句
- 停顿快慢
- 是否更克制或更健谈

### 话题惯性
“嗯 / 哈哈 / 然后呢 / 后来呢”等短反馈不会再把当前话题覆盖掉。
续聊优先沿当前话题推进，不随便突然换话题。

### 不冷，也不机械
本地节奏机会大致倾向：
- 短反馈 / 话题仍在进行：较容易补一句
- 情绪分享：中等偏高
- 普通闲聊：中等
- 已经回答完整的问题：较低
- 明确收尾：不续聊

实际是否继续仍由 DeepSeek 再判断一次，默认是“不继续”。

### 续聊网络失败
第二段如果海鲸等线路偶发网络失败：
- 静默清理
- 短暂停顿后自动重试 1 次
- 仍失败就停止
- 不把续聊失败作为红色聊天错误弹给用户

### 用户发出新消息
没有“正在输入”检测。
只有当用户真正发送了新消息后，旧的续聊才停止。


## v7.6：聊天不易冷场

v7.5 的问题是两层判断都偏保守：
- 本地节奏门控先挡一次
- DeepSeek 又被要求“默认不要继续”

两层叠加后，很多本来可以自然补一句的场景被过早结束。

v7.6 调整为：
- 短反馈：明显更容易自然补一句
- 情绪/日常分享：更愿意承接
- 普通闲聊：适度提高续聊机会
- 明确问题已经答完：仍然较克制
- 明确收尾：仍然停止
- 普通场景仍最多只追加 1 条
- 只有“继续说/多说点”等明确请求才允许多条

同时：
- DeepSeek 不再被提示“默认停止”
- 改为平衡判断“真人此刻会不会自然再补一句”
- 熟悉度与 social_drive 会轻微影响倾向
- 续聊停顿缩短到约 0.85~3.2 秒
- 第一条回复本身也要求“简短但不敷衍”
- 仍未加入用户输入检测


## v7.7：长期聊天行为宪法

本版把“真人感”从概率规则改为因果规则。

核心变化：
- 新增 `SocialConstitution.kt`，把长期聊天原则作为所有正常聊天的稳定行为约束。
- 不再使用随机/概率门控决定是否续聊。
- 普通续聊是否发生，由 DeepSeek 根据当前话题、关系、对话负担、最近聊天和是否有新内容判断。
- 普通场景最多允许 0~2 条续聊；2 条必须对应两步不同的思绪推进。
- 用户明确要求“继续说/多说点”时才允许更多。
- 加入当前设备时间、与上一条消息的时间间隔，帮助模型理解时间已经流动。
- 加入对话负担摘要：最近谁说得更多、联系人最近问了多少问题、当前是谁连续发言。
- 短反馈不会自动变成新话题；共享背景优先省略，不重新介绍。
- 主动聊天移除“每 3 小时一次”的取模规律，改为未完成事件、临近事件或“已有关系 + 确实沉默一段时间”的因果触发。
- 主动消息同样遵守长期聊天行为宪法。
- 不加入“用户正在输入”检测；只在用户真正发送新消息后停止旧续聊。
- AI 身份保持透明，不通过虚构现实经历制造真人感。


## v7.8：逐条社交行为决策

这一版按照“任何额外消息都必须重新证明自己的存在必要”重构。

### 1. 不再预先决定 turns=2
现在：
- 第一条正常回复
- 决策第2条是否值得发
- 第2条真正发出后，重新读取最新聊天状态
- 再重新决策第3条
- 第3条门槛比第2条更高

普通场景最多额外 2 条。
用户明确要求“继续说 / 多说点”时才允许更多。

### 2. 用户话语权优先
本地高优先级识别：
- 用户明显还在讲故事
- 句子以“然后 / 结果 / 就是 / …… ”等未完成形式结尾
- “我跟你说 / 有个事 / 他今天居然……”等明显有后文

这些情况下不主动抢第二条。

### 3. Conversation Pressure
新增 `ai_conversation_pressure` 的实时计算，综合：
- AI / 用户最近字数占比
- AI 连续发言条数
- AI 最近问句数量
- AI 最近一条的长度
- 用户是否在 AI 长回复后明显缩短回复

压力太高时，即使“还有东西能说”也会停止。

### 4. DeepSeek 决策结构
行为决策现在返回：
- continue
- mode
- direction
- novelty
- interruption_risk
- standalone_value
- question

mode 包括：
- reaction
- afterthought
- clarification
- self_share
- followup_question
- topic_extension

这样联系人模型不会把每条第二反应都写成“对了 / 我突然想到”。

### 5. 第二、第三条门槛递增
第2条：
- 至少 medium novelty
- 至少 medium standalone value
- interruption risk 不能 high

第3条：
- 必须 high novelty
- 必须 high standalone value
- interruption risk 必须 low
- conversation pressure 还必须更低

### 6. 等待时间由行为类型决定
不再 `random(0.85~3.2s)`。

大致：
- reaction：约 0.65s 起
- afterthought：约 1.35s 起
- clarification：约 1.7s 起
- followup_question：约 1.9s 起
- topic_extension：约 2.25s 起
- self_share：约 2.7s 起

再根据上一条长度、联系人性格、这是第几条额外消息调整。

### 7. 统一社交行为层
新增：
`SocialBehaviorController.kt`

现在“要不要再说”不再塞在写作模型里。
DeepSeek / 辅助线路负责行为判断；
联系人自己的模型只负责把已经决定好的行为自然表达出来。

仍然没有“用户正在输入检测”。
用户真正发出新消息后，旧的额外消息才会停止。


## v7.9 核心变化

### 1. “要不要继续说”不再依赖 DeepSeek
每个联系人现在用自己的当前路线和模型完成两类工作：

- 行为判断：现在还值不值得继续说；
- 人格表达：如果值得，具体说什么。

例如联系人设置为：
`海鲸AI + grok-4.6`

那么续聊判断和续聊内容都走：
`海鲸AI + grok-4.6`

不会再出现：
`海鲸联系人第一条成功 -> 等 DeepSeek 判断 -> DeepSeek 卡住 -> 联系人不再继续`

`talk_burst` 的每段继续判断也已经改成联系人自己的当前模型。

### 2. 取消“普通聊天最多三条”
普通对话只先生成第一条。
之后每发完一条，都重新读取最新状态并重新判断下一条是否值得存在。

没有“第三条以后强制结束”的正常聊天规则。
代码只保留一个很高的异常死循环保险上限，正常停止依赖内容价值、用户话语权和 conversation pressure。

### 3. 可演化人格
初始人物卡只是人格种子，不再是永久圣旨。

新增 `persona_state`：
- `long_term_rules`：长期相处中学到的规则；
- `temporary_rules`：当前阶段临时调整；
- `temporary_until`：临时规则过期时间。

例如初始设定写“喜欢加表情”，用户后来明确说：
“我不喜欢你老发表情，严肃点。”

联系人会学习新的动态规则，后续：
- 动态规则优先于初始表达习惯；
- “固定结尾加表情 / 每次追问 / 固定几条消息”等旧人物卡动作不再机械执行。

用户说“今天先严肃一点”则更倾向写成临时调整，而不是永久改掉整个人格。

联系人设置页新增“重置动态人格适应”。

### 4. 群聊
消息页顶部新增“发起群聊”。

创建群聊时：
- 至少选择 2 个联系人；
- 可设置群名；
- 群聊信息页可修改群名、增删成员、删除群聊。

群里允许：
- 用户 -> AI；
- AI A -> 用户；
- AI A -> AI B；
- AI B -> AI A；
- 多个 AI 根据当前群聊状态决定谁自然接话。

不是所有 AI 都必须回答用户。

### 5. 群聊身份隔离
群聊不是把所有消息拼成一个 `user` 文本。

数据库每条群消息都保存：
- `sender_kind`
- `sender_key`
- `sender_contact_id`
- `sender_name`
- `group_id`

给模型的上下文使用稳定身份标签，例如：

```text
[USER:user|我]：今天真的无语
[CONTACT:3|小夏]：怎么了
[CONTACT:7|阿深]：先让他说完
[CONTACT:3|小夏]：行
```

因此：
- A 的话只属于 A；
- B 的话只属于 B；
- USER 才代表用户；
- C 如果在群里，会看到 A/B 是两个不同成员；
- C 如果不在这个群里，根本不会获得该群上下文。

### 6. 私聊与群聊数据隔离
私聊仍读取 `messages(contact_id)`。
群聊只读取 `group_messages(group_id)`。

群聊消息不会被写进任何联系人的私聊消息表，也不会作为私聊长期记忆处理。

AI-AI 的群聊消息也不会被当成用户反馈去修改人格。
只有用户本人明确对某个联系人或全群提出聊天偏好时，群聊中的人格适应模块才允许修改该联系人。

### 7. 群聊自己会继续
用户发一条以后，系统会让每个群成员用自己的模型独立判断：
“现在我该不该说话？”

每个成员会给出自己的发言意愿和优先级。
选出最自然的下一位以后生成消息。

新消息发出后，所有成员重新判断，所以可以出现：

用户 -> A -> B -> A -> C -> 停

而不是预先安排“每个 AI 回一次”。

连续 AI 发言越多，继续发言门槛会逐渐升高，避免机器人无限互聊。
代码保留 12 次的异常保护上限，但正常情况下应由模型自然停住。

### 8. 当前群聊范围
v7.9 先实现文字群聊。
私聊原有图片聊天保持不变。


## v8.0 核心变化

### 1. 彻底取消“关系阶段”
不再使用：
- 新建联系人 = 刚认识
- 聊几条 = 逐渐熟悉
- 聊更多 = 很熟

关系直接从：
- 初始人物设定
- 动态人格
- 共享记忆
- 当前真实聊天

中理解。

如果人物一开始就是老朋友、同事、家人、同学等，就直接按那个关系交流。
如果没有指定关系，就保持中性，不自动套“刚认识”。

### 2. 取消“第一阶段 / 第二阶段”回复流程
主回复不再走多阶段生成。

现在是：
- 先自然生成一条当前最该说的内容；
- 发完以后，由 SocialBehaviorController 再判断是否还有下一条值得说；
- 每条都重新判断；
- 不存在“第2阶段、第3阶段”的语义。

`ConversationPlan` 中的 `floor / maxStages / pauseMs / phase` 已移除。

### 3. 不再因为“用户可能还想继续说”而自动停
删除了 `userLikelyHoldsFloor` 逻辑。

现在：
- 不检测用户正在输入；
- 不推测“用户可能还有后文，所以AI先闭嘴”；
- 文字聊天允许双方交叉发送；
- 联系人有自然内容就继续说。

只有：
- 用户明确结束会话；
- 内容已经没有独立价值；
- 重复；
- AI 自己已经造成很高 conversation pressure；

才会自然收住。

### 4. 用户继续发消息不会把AI已经形成的回复作废
以前：
- 用户发新消息
- 旧生成直接取消 / 丢弃

现在：
- 用户可以继续发
- 已经在组织或生成的回复仍然可以发出来
- 新消息会成为后续行为判断的最新上下文

因此可以出现真实文字聊天里的“交叉消息”。

### 5. 同一联系人只保留一条自然续聊链
如果用户在联系人续聊期间又发新消息：
- 不取消原续聊链
- 新消息进入它的最新上下文
- 不额外复制出第二条“续聊控制链”

新的用户消息仍然可以得到自己的首条回应。

### 6. 群聊同样允许交叉消息
群聊里：
- 用户继续发消息不会自动打断 AI-AI 的整个聊天逻辑
- 如果等待期间出现新消息，群聊行为层会用新事件重新判断
- 如果消息是在模型已经生成过程中出现，已经形成的那条仍可正常发送

### 7. 主动聊天不再按消息数量推断关系
后台主动聊天也取消：
- 聊得少 = 关系浅
- 聊得多 = 关系深

这类规则。

主动节奏只把联系人自身的 `social_drive` 作为轻微倾向，
是否主动仍以未完成话题、事件、新联想和真实上下文为主。


## v8.1：海鲸联系人不续聊 / 群聊不发言修复

### 根因
v8.0 中：
- 私聊第一条使用 `streamChat()`；
- “是否继续说”的行为判断使用 `chat()`；
- 群聊成员“是否发言”的判断也使用 `chat()`。

同时行为判断还存在：
- 私聊续聊决策 4.5 秒硬超时；
- 群聊发言决策 5 秒硬超时；
- 异常被 `getOrNull()` 静默转换成“不继续 / 不发言”。

因此 DeepSeek 较快时表现正常；
海鲸/Grok 稍慢、DNS波动或非流式响应格式有差异时，就会看起来像“AI自己不想继续说”。

### 修复
1. 删除 4.5 秒和 5 秒的应用层硬超时；
2. 行为判断仍使用联系人自己的当前模型；
3. 海鲸普通请求增加网络重试；
4. 海鲸普通请求支持两个官方域名：
   - `https://api.haijingai.com/v2/chat/completions`
   - `https://api.atalk-ai.com/v2/chat/completions`
5. 一个域名网络失败时自动尝试另一个；
6. `chat()` 现在同时兼容普通 JSON 与 SSE 文本；
7. 即使请求 `stream=false` 但兼容网关实际返回 `data: ...` 流，也能正常提取回复；
8. 401/403/普通 4xx 不做无意义重试；408/429/5xx 等瞬时错误允许重试/换域名；
9. 私聊第一条流式请求若失败，原有 fallback 会落到新的高可靠 `chat()` 路径。

### 预期结果
- 海鲸联系人：第一条正常；
- 海鲸联系人：后续行为判断不再因为 4.5 秒超时直接停止；
- 海鲸联系人：可以继续自然连发；
- 海鲸群成员：可以参与群聊、回复用户或另一个AI；
- DeepSeek联系人：原有行为保持。


## v8.2：统一系统行为判断模型

### 新增“系统行为判断模型”
在：
`我 → 设置 → AI 服务`

新增：
- 系统行为判断 API 路线：海鲸AI / DeepSeek 官方
- 系统行为判断模型 ID

这个模型只负责“行为决策”，不负责替联系人写聊天内容。

### 私聊
流程变成：

用户消息
→ 联系人自己的模型生成第一条
→ 系统行为判断模型判断“还要不要继续”
→ 如果继续
→ 联系人自己的模型生成下一条
→ 再由系统行为判断模型重新判断

因此：
- A 可以继续用海鲸 Grok 聊天；
- B 可以继续用 DeepSeek 聊天；
- 但 A/B 是否继续说，都由同一个系统行为判断模型统一决定。

### 群聊
v8.1：
每一步 A/B/C 都分别调用自己的模型判断“我要不要说”
→ 再选一个人
→ 被选中的模型生成内容

v8.2：
每一步只调用 **1 次系统行为判断模型**
→ 系统模型直接决定：
  - stop，或者
  - 哪个 CONTACT 说
  - 回应谁
  - 属于 reaction / reply / clarify / self_share / topic_extend / question
  - 等待节奏
→ 然后只调用被选中联系人的聊天模型生成真正消息

例如群里有 A、B、C：

系统判断模型：
`下一位 B，回应 A 的观点`

然后：
只调用 B 自己设置的模型生成 B 的消息。

下一步再次：
只调用 1 次系统判断模型决定下一位或停止。

### 调用量变化
群聊每产生一条 AI 消息，行为层从大致：

N 个联系人判断调用 + 1 个生成调用

变成：

1 个系统判断调用 + 1 个被选中联系人的生成调用

群成员越多，节省越明显。

### 保留
- 私聊/群聊身份隔离；
- 动态人格；
- 群里 AI 可以回复另一个 AI；
- 用户继续发消息不会强制打断联系人；
- 无“刚认识→熟悉”关系阶段；
- 无第一阶段/第二阶段回复流程；
- 海鲸 JSON/SSE 兼容、重试和备用官方入口。


## v8.3：修复私聊不连发、群聊一人一句

### 根因
v8.2 虽然已经统一使用“系统行为判断模型”，但仍继承了早期的保守规则：

- 私聊：第2条、第3条存在本地递增门槛；
- `novelty / standalone_value / interruption_risk` 会再次筛掉系统模型已经允许的续聊；
- conversation pressure 还有硬停止条件；
- 群聊提示词明确写了“AI连续越多，继续理由越强”；
- 群聊将连续AI消息数量作为节奏压力；
- 这会让系统模型自然形成“每人说一句 → 差不多该停”的模式。

### v8.3 改动

#### 私聊
- 删除第2条/第3条递增硬门槛；
- 删除 `passesThreshold()`；
- 删除本地 conversation-pressure 硬停止；
- 系统行为模型直接判断“聊天动量还在不在”；
- 不再给 `novelty / standalone_value / interruption_risk` 打分；
- 系统模型只输出：
  - continue
  - mode
  - direction
  - question
  - delay_class
- 系统模型判断继续后，联系人自己的模型直接生成下一条；
- 不因“这是第几条”提高停止倾向。

#### 群聊
- 明确禁止 round-robin / 公平轮流：
  - 不要求 A、B、C 每人说一句；
  - A 可以连续说多条；
  - A/B 可以互相聊很多轮；
  - C 可以整个话题都不说；
- “已经连续多少条 AI 消息”只作为背景，不再是停止理由；
- 只要最新消息仍产生自然反应、反驳、补充、追问、玩笑或观点推进，就保持聊天动量；
- 只有话题真的落地、无人有新内容、继续只会复述/凑话时才 stop；
- 群聊仍然每一步只调用一次系统行为判断模型，然后只调用被选中联系人的模型生成内容。

#### 保险上限
- 私聊普通续聊安全上限提高到 40 次；
- 明确“继续说”安全上限提高到 64 次；
- 群聊异常安全上限提高到 48 次；
- 这些只是防止模型异常死循环，不是正常聊天条数规则。
